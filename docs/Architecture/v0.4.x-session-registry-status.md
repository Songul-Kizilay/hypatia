# v0.4.x Session Registry Architecture Status

> Stable session lifecycle contract for Hypatia after Sprint 4.3.

---

# Purpose

This document records the architectural boundaries and behavioural guarantees
introduced by the persistent session registry.

It defines how registered sessions, active-session selection, request-level
overrides, and session-scoped recall work without changing the memory record
model or memory persistence schema.

---

# High-Level Architecture

```text
Brain
-> CognitiveEngine
   -> SessionManager
      -> SessionStore
         -> JsonFileSessionStore
            -> data/sessions/sessions.json
   -> MemoryManager
      -> JsonFileMemoryStore
         -> data/memory/memory.json
-> ResponseComposer
-> BrainResponse
```

---

# Responsibility Boundaries

## SessionManager

- Owns the session registry and active-session state.
- Normalizes command session IDs by trimming whitespace.
- Preserves session ID case and uses case-sensitive matching.
- Creates sessions, selects the active session, and lists registry records.
- Coordinates transactional registry persistence and session domain events.

## SessionStore

- Defines complete registry snapshot loading and saving only.
- Does not own active-session policy, command parsing, events, or request flow.

```python
load() -> SessionRegistrySnapshot | None
save(snapshot: SessionRegistrySnapshot) -> None
```

## JsonFileSessionStore

- Owns JSON schema validation and serialization.
- Owns filesystem access, temporary-file cleanup, flush, fsync, and atomic replacement.
- Rejects malformed or invalid registry data through SessionError.

## CognitiveEngine

- Orchestrates explicit session commands and request-level session overrides.
- Does not own registry state or persistence behaviour.
- Requires an explicitly injected SessionManager dependency.
- Does not create, own, or silently substitute session state.
- Does not create user-facing session messages directly.

## ResponseComposer

- Owns all user-visible create, list, activate, duplicate, and failure responses.

## Bootstrap

- Loads the session registry before persistent memory.
- Injects the same persistent SessionManager instance into CognitiveEngine and
  registers it in the dependency container.
- Publishes no runtime container until both loads have succeeded.

# Session Registry Contract

The default registry path is:

```text
data/sessions/sessions.json
```

The path is resolved from the project root, not the current working directory.

Each registry contains an active session ID and an ordered list of immutable
session records. The `default` session is mandatory.

```json
{
  "schema_version": 1,
  "active_session_id": "default",
  "sessions": [
    {
      "session_id": "default",
      "created_at": "2026-08-04T15:00:00+00:00"
    }
  ]
}
```

Session IDs are trimmed but case-preserving and case-sensitive. For example,
`Work-1` and `work-1` are different sessions.

---

# Transactional Mutation Guarantee

Session creation and active-session changes follow this order:

```text
candidate registry
-> persistent save
-> in-memory commit
-> session domain event
```

On success, disk, registry memory, active-session state, and events represent
the new state.

On persistence failure, disk and in-memory registry state remain unchanged,
no session event is emitted, and SessionError is returned to the caller.

Duplicate creation and selecting the already active session are successful
no-ops: they do not write persistence or emit events.

---

# Request Session Resolution

Session selection is resolved by CognitiveEngine for normal conversation and
explicit recall.

```text
request metadata session_id is present
-> validate string type
-> trim
-> validate registry membership
-> use as a request-only override

session_id missing, None, empty, or whitespace
-> use SessionManager.get_active()
```

An override never changes the active session. Non-string and unknown overrides
return controlled failure responses without memory, persistence, search, or
lifecycle side effects.

Legacy memory records without `metadata["session_id"]` continue to belong to
the `default` session. Records with an explicit null session ID are not treated
as legacy records.

---

# Commands and Events

Only deterministic command forms are recognised:

```text
create session <id>
list sessions
use session <id>
```

Natural-language phrases containing similar words remain normal conversation.
Session commands do not create conversation memory records or `brain.*`
lifecycle events.

Successful mutations emit only these session domain events after persistence:

```text
session.created
session.activated
```

Listing and duplicate creation emit no event.

---

# Bootstrap and Failure Behaviour

Bootstrap initializes runtime state in this order:

```text
EventBus
-> JsonFileSessionStore
-> SessionManager.load()
-> JsonFileMemoryStore
-> MemoryManager.load()
-> remaining runtime components
-> container registration
```

When no session file exists, SessionManager creates and atomically persists a
default registry before Bootstrap continues.

Malformed session JSON, unsupported schema versions, invalid dates, duplicate
IDs, missing `default`, or an unknown active session raise SessionError. A
session-load failure prevents memory loading and container publication. A
memory-load failure also prevents container publication.

# Compatibility

- MemoryRecord remains unchanged.
- Memory JSON schema remains version 1.
- MemoryManager.search() remains unchanged.
- Session metadata remains stored only within MemoryRecord metadata.
- Existing session-less conversation records remain visible to default-session recall.
- RAM-only MemoryManager behaviour remains supported.

# Deferred Capabilities

The following capabilities are intentionally outside Sprint 4.3:

- session deletion
- session rename
- automatic session discovery
- cross-session recall
- automatic recall
- conversation summaries
- semantic retrieval
- LLM integration
- session encryption
- multi-process coordination and file locking

---

# Completion Statement

Sprint 4.3 establishes a persistent, transactional session registry with
explicit active-session selection and request-local overrides. It extends the
existing cognitive and memory contracts without changing MemoryRecord or the
memory persistence schema.
