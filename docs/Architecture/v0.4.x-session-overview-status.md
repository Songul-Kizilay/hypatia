# v0.4.x Session Overview Architecture Status

> Deterministic, registry-wide session visibility contract for Hypatia after
> Sprint 4.6.

---

# Purpose

This document records the architectural boundaries and behavioural guarantees
for explicit session overview. It makes registered sessions and their normal
conversation counts visible without changing session state, memory state, or
persistence formats.

---

# Command Contract

Only this deterministic command form is recognised:

```text
session overview
```

Recognition is case-insensitive. Natural-language phrases that merely discuss
sessions or their contents remain normal conversation.

---

# Responsibility Boundaries

## BrainRouter

- Recognises only the explicit `session overview` command.
- Does not resolve sessions, count records, or access memory.

## CognitiveEngine

- Owns read-only conversation-count aggregation.
- Reads the registered-session order from `SessionManager.list()`.
- Reads the persisted active session from `SessionManager.get_active()`.
- Reads active memory records through exactly one `MemoryManager.all()` call.
- Filters eligible records and counts them only for registered string session
  IDs.
- Delegates all user-visible presentation to ResponseComposer.

## SessionManager

- Remains the owner of registered sessions and persisted active-session state.

## MemoryManager

- Remains the source of active memory records through `all()`.
- Retains ownership of expiry cleanup and existing memory lifecycle events.

## ResponseComposer

- Owns the deterministic session overview response.
- Preserves the registry order it receives.
- Formats zero, singular, and plural conversation counts.

No persistence schema changes are introduced by this capability.

---

# Aggregation Contract

Session overview always applies aggregation in this exact order:

```text
SessionManager.list()
-> registered session IDs initialised to 0
-> MemoryManager.all()
-> tags include brain + conversation
-> missing session_id treated as default
-> registered string session ID count
-> ResponseComposer
```

Only records whose tags include both `brain` and `conversation` are eligible.
Knowledge-search records, planning records, session commands, and other
internal memory kinds are excluded by this tag contract.

Session order is always the `SessionManager.list()` order. The overview does
not apply alphabetical, count-based, creation-time, or active-session-first
sorting.

---

# Session Metadata Contract

Legacy memory records with no `metadata["session_id"]` are counted for the
`default` session.

Records with an explicit `metadata["session_id"] is None`, a non-string
session ID, or an orphan string ID that is not registered are not counted for
any visible session. They do not create additional overview rows.

`session overview` is registry-wide rather than session-scoped. It never calls
request-level session resolution:

```text
request metadata session_id
-> ignored entirely
```

This includes registered, unknown, empty, null, and non-string override
values. The active marker always reflects the actual persisted active session.

---

# Response Contract

ResponseComposer presents each registered session in registry order:

```text
Sessions:
1. default — 0 conversations
2. work-1 — 1 conversation [active]
3. research — 8 conversations
```

Only the session whose ID equals the persisted active-session ID receives the
`[active]` marker. The response has intent `session_overview`, succeeds, and
uses `memory_count` for the total of eligible records across displayed
registered sessions. Orphan counts are excluded from that total.

---

# Lifecycle and Side Effects

The `session overview` command produces no new:

- conversation memory write
- session write
- persistence write
- active-session change
- `brain.*` lifecycle event
- session domain event

`MemoryManager.all()` may perform its existing expiry cleanup and may emit
existing memory expiry events. This is inherited memory lifecycle behaviour,
not a session-overview lifecycle event.

---

# Persistence and Restart Behaviour

Session overview reuses the existing persistent memory and session registry
contracts without changing them. After Bootstrap reloads both stores, registry
order, active-session marking, legacy-aware counts, and read-only behaviour
remain the same.

```text
MemoryRecord unchanged
memory.json schema v1 unchanged
sessions.json schema v1 unchanged
SessionManager unchanged
JsonFileMemoryStore unchanged
JsonFileSessionStore unchanged
```

---

# Deferred Capabilities

The following are intentionally outside Sprint 4.6:

- session deletion
- session rename
- per-session latest-conversation timestamps
- orphan memory reporting
- memory size or disk usage reporting
- session descriptions
- session export
- cross-session search
- session sorting or filtering options
- session statistics history

---

# Completion Statement

Sprint 4.6 adds deterministic, restart-safe visibility into registered
sessions and their normal conversation counts. It preserves registry order,
active-session ownership, legacy memory behaviour, and existing persistence
contracts without introducing new writes or lifecycle side effects.
