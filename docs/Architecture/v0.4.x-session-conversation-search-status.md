# v0.4.x Session Conversation Search Architecture Status

> Deterministic, session-aware lexical conversation search contract for
> Hypatia after Sprint 4.5.

---

# Purpose

This document records the architectural boundaries and behavioural guarantees
for explicit conversation search. It provides session-scoped retrieval of
normal conversation records without introducing semantic ranking, automatic
recall, or new persistence formats.

---

# Command Contract

Only these deterministic command forms are recognised:

```text
search conversations
search conversations <query>
```

Natural-language phrases that merely discuss searching conversations remain
normal conversation.

An empty query produces the controlled response:

```text
Search query must not be empty.
```

---

# Responsibility Boundaries

## BrainRouter

- Recognises only the explicit conversation-search command.
- Does not extract queries, resolve sessions, or access memory.

## CognitiveEngine

- Routes conversation search ahead of generic knowledge search.
- Extracts and validates the query.
- Resolves the request session.
- Calls `MemoryManager.search(query, limit=None)`.
- Filters records by tags and resolved session.
- Selects the first five filtered results without changing relevance order.

## MemoryManager

- Owns the existing lexical and relevance search behaviour.
- Retains ownership of expiry cleanup and existing memory lifecycle events.

## ResponseComposer

- Owns all user-visible conversation-search results, empty, and failure
  responses.
- Presents stored record content without transformation.

---

# Routing Order

The cognitive request flow applies this order:

```text
conversation_search
-> generic knowledge search
-> plan
-> recall
-> session commands
-> recent conversations
-> normal conversation
```

This prevents `search conversations <query>` from being captured by the
generic knowledge-search path.

---

# Record Selection Contract

Conversation search applies selection in this exact order:

```text
MemoryManager.search(query, limit=None)
-> tags include brain + conversation
-> resolved session filter
-> relevance order preserved
-> first 5
```

The result limit is never applied before tag filtering or session filtering.

Conversation search does not alter the returned relevance ordering:

```text
No created_at sorting
No alphabetical sorting
No content sorting
No reranking
```

Only records whose tags include both `brain` and `conversation` are eligible.
Knowledge-search records, planning records, session commands, and other
internal memory kinds are excluded by this tag contract.

---

# Session Resolution Contract

```text
registered request-level override
-> request-only session

missing / None / blank override
-> active session
```

An override never changes the active session.

Legacy memory records with no `metadata["session_id"]` belong to the `default`
session. Records with an explicit `metadata["session_id"] is None` are not
legacy records and match no normal string session.

---

# Response Contract

Conversation search presents existing records rather than generating an
interpretation of them.

```text
record.content is presented unchanged
no summarization
no rewriting
no trimming
no normalization
no match highlighting
```

ResponseComposer adds only a deterministic session heading and result
numbering.

---

# Lifecycle and Side Effects

The `search conversations` command produces no new:

- conversation memory write
- persistence write
- active-session change
- `brain.*` lifecycle event
- session domain event

`MemoryManager.search()` may retain its existing expiry cleanup and existing
memory expiry event behaviour. This is inherited memory lifecycle behaviour,
not a conversation-search lifecycle event.

---

# Persistence Compatibility

Conversation search reuses the existing persistent memory and session
contracts without changing them.

```text
MemoryRecord unchanged
memory.json schema v1 unchanged
sessions.json schema v1 unchanged
SessionManager unchanged
JsonFileMemoryStore unchanged
JsonFileSessionStore unchanged
```

After Bootstrap reloads both stores, the same session filtering, relevance
order, first-five limit, and read-only behaviour apply.

---

# Deferred Capabilities

The following are intentionally outside Sprint 4.5:

- semantic search
- vector embeddings
- LLM ranking
- cross-session search
- pagination
- custom result count
- date filtering
- match highlighting
- automatic recall
- conversation summaries
- fuzzy correction
- side-effect-free memory search API

---

# Completion Statement

Sprint 4.5 adds deterministic, restart-safe lexical search of normal
conversation records in the resolved session. It preserves MemoryManager
relevance ordering and existing persistence contracts while adding no new
lifecycle side effects.
