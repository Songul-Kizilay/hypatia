# Hypatia v0.4.x Targeted Session Conversation Search Status

> Stable architectural contract for deterministic, read-only lexical search of a command-selected session.

## Purpose

`session search <session-id> -- <query>` finds up to five normal conversation
records in one registered session. It does not use request metadata or the
persisted active session to choose its target.

## Command Contract

Only this explicit command family is recognized:

```text
session search
session search <suffix>
session search <session-id> -- <query>
```

The first exact `" -- "` separator divides the suffix. The session ID and
query are trimmed only at their outer boundaries; their case and inner
whitespace are preserved. Session lookup is exact and case-sensitive.

```text
session search work research -- persistence contract
-> session ID: work research
-> query: persistence contract
```

The following failures are produced before any memory read:

```text
Search query separator is required: --
Session ID must not be empty.
Search query must not be empty.
Unknown session: <session-id>
```

There is no user-provided result count. The limit is always five.

## Routing Contract

`BrainRouter` recognizes only the explicit `session search` command family.
`CognitiveEngine` handles `session_search` before generic knowledge search:

```text
conversation_search
-> session_search
-> generic knowledge search
-> plan
-> recall
-> session commands and read-only session commands
-> recent conversations
-> normal conversation
```

This prevents `session search <session-id> -- <query>` from being consumed by
the generic knowledge-search flow.

## Responsibility Boundaries

```text
BrainRouter
-> explicit command recognition only

CognitiveEngine
-> parsing and validation
-> exact registered-session lookup
-> one memory search, tag/session filtering, and fixed limit

MemoryManager
-> existing lexical search and relevance ordering

ResponseComposer
-> all user-visible results, empty, and failure responses
```

## Session Resolution

The target session comes only from the command suffix.

```text
request metadata is ignored
active session is ignored
_resolve_session_id() is not called
```

Therefore metadata, including a missing, invalid, or non-string
`metadata["session_id"]`, cannot override the target session or create a
failure. The command does not call `SessionManager.get_active()`.

## Memory Search Flow

For a validated, registered target session the complete flow is:

```text
MemoryManager.search(query, limit=None) exactly once
-> tags include brain + conversation
-> legacy-aware target-session filter
-> preserve MemoryManager relevance order
-> first 5
-> session_search ResponseComposer method
```

`MemoryManager.all()` is not called. The engine applies no `created_at`,
alphabetical, content-based, or secondary relevance sort and performs no
reranking.

## Filtering Rules

Only records whose tags include both `brain` and `conversation` are eligible.

For target `default`, a record with a missing `metadata["session_id"]` is
legacy data and matches. An explicit string value of `"default"` also matches.
For every other target, only an exactly equal string value matches.

An explicit `session_id` value of `None`, any non-string value, another
session, or an orphan session ID matches no normal string target. Missing
session metadata does not match a custom target.

## Ordering and Limit

The relevance order returned by `MemoryManager.search()` is retained. The
five-record limit is applied only after tag and target-session filtering.

## Composer Contract

`ResponseComposer` owns three separate methods:

```text
session_search_results
session_search_empty
session_search_failure
```

Every response has `intent="session_search"` and preserves `request_id`.

```text
Results: success=True, memory_count=len(records)
Empty:   success=True, memory_count=0
Failure: success=False, memory_count=0
```

Results render records in the received order:

```text
Conversation matches in work research for "persistence":
1. <record.content>
```

Record content is presented unchanged: no summarization, rewriting, trimming,
normalization, or match highlighting is performed.

## Read-Only Guarantees

`session_search` itself creates no conversation memory record, memory write,
session write, persistence write, active-session change, `brain.*` lifecycle
event, or session event.

`MemoryManager.search()` may retain its existing expiry cleanup and memory
expiry event behavior. That is inherited memory lifecycle behavior, not a new
`session_search` lifecycle event.

## Persistence and Restart Behavior

No persistence schema or runtime wiring changes are introduced:

```text
MemoryRecord unchanged
SessionRecord unchanged
memory.json schema v1 unchanged
sessions.json schema v1 unchanged
SessionManager unchanged
JsonFileMemoryStore unchanged
JsonFileSessionStore unchanged
Bootstrap wiring unchanged
```

After Bootstrap reloads persisted memory and sessions, target-session search
uses the same filtering, relevance ordering, fixed limit, and read-only
behavior.

## Out of Scope

- Semantic search, vector embeddings, or LLM ranking
- Cross-session search
- Custom result counts, pagination, or date filters
- Match highlighting or fuzzy query correction
- Automatic recall or conversation summaries
- Session deletion or rename
- A side-effect-free MemoryManager search API

## Test Coverage

Coverage includes explicit routing, generic-search priority, separator and
failure validation, exact session matching, inner-space IDs, ignored metadata
and active state, one `search(query, limit=None)` call, legacy filtering,
relevance-order preservation, post-filter limiting, read-only behavior, and
Bootstrap restart regression coverage.

## Completion Statement

Hypatia can search normal conversation records in an explicitly named,
persisted session while preserving lexical relevance order and leaving memory,
session, persistence, and active-session state unchanged.
