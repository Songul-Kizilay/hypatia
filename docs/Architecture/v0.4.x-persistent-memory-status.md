# v0.4.x Persistent Memory Architecture Status

> Stable persistence contract for Hypatia's local memory foundation after Sprint 4.1.

---

# Purpose

This document records the architectural status and behavioural contracts introduced by Sprint 4.1.

It defines the boundaries of persistent local memory, the guarantees that future work must preserve, and the capabilities that remain intentionally deferred.

---

# Design Principles

- MemoryManager remains the owner of memory records and domain behaviour.
- Persistence is optional.
- Storage concerns remain isolated behind the MemoryStore boundary.
- Mutations are committed only after persistence succeeds.
- Startup must fail explicitly when persisted memory is corrupted.
- Existing RAM-only and explicit recall behaviour remains compatible.

---

```text
Brain
→ CognitiveEngine
→ MemoryManager
   ↓ optional
MemoryStore

```

---

# Responsibility Boundaries

## MemoryManager

- Owns active memory records.
- Owns CRUD behaviour.
- Owns search ordering and tag filtering.
- Owns TTL and expiry policy.
- Owns lifecycle event publication.
- Coordinates transactional mutation ordering.
- Remains usable without a persistent store.

## MemoryStore

- Defines snapshot loading and saving only.
- Does not own search, expiry, events, or memory domain rules.

```python
load() -> list[MemoryRecord]
save(records: list[MemoryRecord]) -> None
```

## JsonFileMemoryStore

- Owns JSON serialization and parsing.
- Owns schema validation.
- Owns filesystem access.
- Owns temporary-file creation and cleanup.
- Owns flush, fsync, and atomic replacement.
- Rejects corrupted or unsupported data through MemoryError.

---

# Persistence Contract

Persistence uses complete snapshots rather than incremental record operations.

The default path is:

```text
data/memory/memory.json
```

The path is resolved from the project root rather than the current working directory.

---

# Transactional Mutation Guarantee

Persistent mutations follow this order:

```text
candidate snapshot
→ persistent save
→ in-memory commit
→ lifecycle event
```

On success:

```text
disk, memory, and lifecycle events represent the new state
```

On persistence failure:

```text
disk remains unchanged
memory remains unchanged
no lifecycle event is emitted
MemoryError is returned to the caller
```

This guarantee applies to:

- add
- update
- successful delete
- clear

---

# Startup and Load Behaviour

Bootstrap creates and loads memory in this order:

```text
JsonFileMemoryStore
→ MemoryManager
→ MemoryManager.load()
→ remaining runtime components
→ container registration
```

The runtime container is not published before memory loading succeeds.

Load behaviour:

- A missing file produces an empty snapshot.
- A valid snapshot completely replaces current in-memory records.
- Loaded records are not merged with existing records.
- Expired records are filtered by MemoryManager.
- Load does not emit record lifecycle events.
- A failed load preserves the previous in-memory state.
- Corrupted persistence prevents Bootstrap from completing.

# JSON Schema v1

```json
{
  "schema_version": 1,
  "records": [
    {
      "memory_id": "...",
      "content": "...",
      "metadata": {},
      "tags": ["brain", "conversation"],
      "created_at": "2026-08-04T12:00:00+00:00",
      "updated_at": "2026-08-04T12:00:00+00:00",
      "expires_at": null
    }
  ]
}
```

Schema rules:

- schema_version must equal 1.
- records must be a list.
- memory_id values must be unique.
- tags are persisted as sorted JSON lists.
- datetime fields use timezone-aware ISO-8601 strings.
- expires_at may be null.
- metadata must be JSON-serializable.
- malformed JSON and invalid record fields raise MemoryError.

# Atomic Write Contract

JsonFileMemoryStore writes snapshots through:

```text
create parent directory
→ create temporary file in target directory
→ write UTF-8 JSON
→ flush
→ fsync
→ atomic replace
→ clean temporary file
```

The existing memory file is not replaced until the new snapshot has been written successfully.

---

# Failure Behaviour

The runtime does not silently discard, repair, or overwrite corrupted memory.

The following conditions raise MemoryError:

- malformed JSON
- unsupported schema version
- invalid document structure
- missing or invalid record fields
- invalid timezone information
- duplicate memory IDs
- non-serializable metadata
- filesystem read or write failures

Bootstrap stops instead of silently starting with empty memory when an existing file is invalid.

---

# Backward Compatibility

MemoryManager remains compatible with RAM-only construction:

```python
MemoryManager()
MemoryManager(event_bus)
```

When no store is provided:

- load is a no-op
- mutations remain memory-only
- the existing public API is preserved
- event behaviour remains unchanged

The following public APIs remain available:

```text
add
get
update
delete
search
all
count
clear
load
```

---

# Explicit Recall Integration

Explicit recall continues to use MemoryManager.search().

A conversation record persisted during one process can be retrieved after a later Bootstrap initialization.

Recall remains explicit:

```text
recall <query>
```

Knowledge-search records remain excluded from conversation recall through the existing tag contract.

Persistent memory does not introduce automatic recall, implicit context injection, summarization, or semantic retrieval.

# Deferred Capabilities

The following capabilities are intentionally outside the v0.4.x persistent-memory foundation:

- encryption at rest
- schema migration framework
- multi-process write coordination
- file locking
- cloud synchronization
- deleted-record history
- automatic recall
- semantic retrieval
- memory summarization
- LLM-driven memory selection

---

# Sprint 4.2 Entry Criteria

Any future memory capability must preserve:

- optional persistence
- MemoryStore responsibility boundaries
- transactional mutation ordering
- startup failure behaviour
- atomic file replacement
- RAM-only compatibility
- explicit recall filtering
- deterministic tests
- import safety

A future capability must not combine persistence changes with LLM, RAG, automatic recall, or unrelated orchestration changes unless its scope is separately reviewed and approved.
